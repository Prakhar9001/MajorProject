1. Introduction and Document Purpose
1.1 Document Overview
This Architecture Document provides a comprehensive, structured, and technically precise description of the software architecture underlying the Deepfake Detection System developed as a B.Tech major project at SRM Institute of Science and Technology. The document covers all architectural dimensions of the system: the selected architectural pattern and its justification, the application layer decomposition, data flows, component relationships, use cases, class structures, sequence interactions, deployment infrastructure, security posture, and performance considerations.
The primary audience for this document includes the student development team, academic supervisors, and external evaluators conducting project assessment. It is intended to serve as the authoritative technical reference against which the implemented system can be evaluated for architectural compliance and design quality.
All architectural decisions described in this document are grounded in the specific technical requirements of a machine learning inference system that must provide real-time binary classification of facial imagery, integrate explainability through Grad-CAM, and expose results via a REST API and web-based user interface. Where applicable, decisions are justified with reference to the project's performance targets, computational constraints, and academic evaluation criteria.
1.2 Scope
The scope of this architecture document encompasses the entire technology footprint of the Deepfake Detection System. This includes the machine learning model training and evaluation pipeline, the inference backend service, the explainability engine, the web frontend, and the deployment infrastructure. The document does not cover the academic research methodology in detail, as that is addressed in the companion IEEE Access research paper. However, architectural decisions that arise directly from research findings — such as the choice of EfficientNet-B0 as the backbone, the two-phase fine-tuning protocol, and the multi-source training corpus — are described in architectural terms.
The system is designed for academic demonstration and reproducible research, not for large-scale commercial production deployment. However, the architecture intentionally follows production-grade patterns — including RESTful API design, modular service decomposition, and containerization — to demonstrate professional software engineering practice and to facilitate future scaling if required.

2. Architecture Pattern Selection
2.1 Selected Pattern: Monolithic Architecture with Modular Internal Layers
The Deepfake Detection System is implemented using a Monolithic Architecture with clearly defined internal modular layers. All system components — the ML model, preprocessing pipeline, Grad-CAM explainability engine, FastAPI REST backend, and Streamlit frontend — are deployed as a single, cohesive application unit. This is the most appropriate architectural pattern for this project given its academic scope, single-team ownership, and the tightly coupled nature of the ML inference pipeline.
While the system is architecturally monolithic in its deployment topology, it maintains strong internal modularity through clearly delineated functional layers, well-defined interfaces between components, and separation of concerns at the code level. This 'modular monolith' approach provides the operational simplicity of a single-process deployment while preserving the code-level maintainability associated with microservices.
2.2 Justification for Monolithic Architecture
The selection of monolithic architecture is justified by several factors specific to this project. First, the system's core operation — ML inference — is inherently sequential and tightly coupled: face detection feeds preprocessing, which feeds the model, which feeds Grad-CAM, which feeds the API response. This tight coupling provides no meaningful performance benefit from service decomposition.
Second, the academic context does not require independent scaling of individual components. The system handles single or small batches of image and video inference requests in an educational setting, not millions of concurrent API calls requiring horizontal scaling. A microservices architecture would introduce network latency between services, operational complexity in orchestration, and significant overhead in inter-service communication that would negatively impact inference latency without providing compensating benefits.
Third, the deep learning model is a single serialized artifact (PyTorch .pt file) that is loaded once at application startup and held in GPU memory. Splitting this across services would require expensive model serialization and deserialization on every inference call, potentially increasing per-image latency from 87ms to several hundred milliseconds due to network and serialization overhead.
Fourth, the team size of two student developers is optimally suited to a monolithic codebase. Managing multiple independently deployed microservices, each with its own CI/CD pipeline, container registry, and service mesh configuration, would be disproportionately complex for a two-person academic team.
2.3 Comparative Analysis of Architectural Alternatives
2.4 Internal Architectural Layers
Despite the monolithic deployment topology, the system is structured into five distinct internal architectural layers, each with clearly defined responsibilities and interfaces. These layers enforce separation of concerns, facilitate independent testing of components, and allow for future extraction into microservices if the project scope expands.
Presentation Layer: Streamlit web application providing the user-facing interface for image/video upload, prediction display, heatmap visualization, metrics browsing, and report export.
API Gateway Layer: FastAPI application providing the REST interface, request validation, response serialization, and routing between business logic components.
Inference Engine Layer: EfficientNet-B0 model and classification head performing binary deepfake classification on preprocessed face tensors.
Explainability Layer: Grad-CAM engine computing gradient-weighted activation maps and facial sub-feature score analysis on inference outputs.
Data Processing Layer: MTCNN face detection, geometric alignment, augmentation, normalization, and frame extraction pipeline.
2.5 Architectural Quality Attributes
The monolithic architecture with modular internal layers satisfies the following quality attributes required by the project: Performance — single-process execution eliminates inter-service network overhead, keeping image inference latency at 87ms on GPU; Maintainability — modular internal structure enables individual components to be modified independently without affecting the full system; Testability — each layer exposes well-defined interfaces that can be unit-tested in isolation; Deployability — a single Docker container encapsulates the entire system, simplifying deployment to any CUDA-enabled host; Reproducibility — a single codebase with pinned dependency versions ensures that experimental results can be reproduced reliably.

3. System Overview
3.1 System Purpose and Context
The Deepfake Detection System is an AI-powered forensic tool designed to classify facial images and video frames as either authentic (real) or AI-synthetically generated (fake). The system addresses the growing threat of deepfake media by providing automated, explainable, and reproducible detection capabilities accessible through both a programmatic API and an educational web interface. It is positioned as a research demonstration platform rather than a production-scale content moderation service.
The system occupies the intersection of three technical domains: computer vision and deep learning (for classification), explainable AI (for interpretability), and full-stack web development (for accessibility). Its architecture must therefore satisfy the requirements of all three domains simultaneously, balancing the computational intensity of GPU-accelerated inference with the responsiveness requirements of a web application.
3.2 High-Level System Boundary
The system boundary encompasses all software components from user input to prediction output. External entities that interact with the system include human users via the Streamlit web browser interface, API clients via HTTP requests to the FastAPI server, and the file system from which pre-trained model weights are loaded at startup. External dependencies include the MTCNN face detection library, the PyTorch deep learning framework, and the timm model registry from which EfficientNet-B0 is sourced.
The system does not have persistent database storage. All inference state is ephemeral within the scope of a single API request. Pre-computed cross-dataset benchmark metrics are stored as static JSON fixtures and served by the /metrics endpoint. Training data is consumed offline during the model training phase and is not part of the runtime system boundary.
3.3 System Constraints
Hardware Constraint: Production inference requires CUDA-capable GPU with minimum 8GB VRAM. CPU-only inference is supported but latency constraints (87ms GPU vs >1000ms CPU) are not guaranteed.
Model Scope Constraint: Detection is scoped to GAN-based and encoder-decoder facial manipulation applied to real source videos. Text-to-image synthesis, avatar systems, and non-facial media are not in scope.
Input Constraint: Images must contain at least one detectable human face with MTCNN confidence >= 0.9. Multi-face images are processed using the highest-confidence detection only.
Temporal Constraint: The current system processes video frames independently without temporal modelling. Frame-level predictions are aggregated statistically rather than through recurrent or transformer-based temporal fusion.
Scale Constraint: The system is designed for interactive single-user inference, not concurrent bulk processing. No load balancing, request queuing, or horizontal scaling is implemented in the current version.
3.4 Key Technical Decisions
Several key technical decisions shape the overall system architecture. The choice of EfficientNet-B0 as the backbone balances accuracy with parameter efficiency — achieving 99.41% in-domain accuracy with only 5.3M parameters compared to ResNet-50 (25.6M) or XceptionNet (22.9M). This choice directly affects inference latency, VRAM requirements, and the feasibility of deployment on resource-constrained hardware.
The decision to use PyTorch rather than TensorFlow is driven by the project's research orientation: PyTorch's dynamic computational graph, superior debugging tooling, and prevalence in the deepfake detection research community make it the natural choice. The timm (PyTorch Image Models) library provides access to a pre-trained EfficientNet-B0 checkpoint trained on ImageNet-1k, which forms the starting point for domain-specific fine-tuning.
The decision to use FastAPI over Flask or Django REST Framework is motivated by FastAPI's native async support, automatic OpenAPI schema generation, and superior request validation via Pydantic models. Streamlit is chosen for the frontend over React or Vue.js because it enables rapid development of data-science-oriented UIs in pure Python, eliminating the need for JavaScript development expertise.

4. Application Architecture
4.1 Frontend Layer – Streamlit Application
The frontend layer is implemented as a Streamlit web application that serves as the primary human interface for the Deepfake Detection System. Streamlit renders a single-page application in the user's browser, communicating with the FastAPI backend over HTTP on the local network. The frontend is structured into seven functionally distinct modules, each implemented as a separate Streamlit page section or sidebar panel.
4.1.1 Prediction Panel Module
The Prediction Panel is the core interactive module. It accepts user-uploaded images via a Streamlit file uploader widget, transmits the image to the FastAPI /predict/image endpoint via a POST request, and renders the prediction results. The panel displays: the original uploaded image alongside the Grad-CAM heatmap overlay, the binary prediction label (REAL / FAKE) with color-coded indicator, a circular confidence gauge showing the model's output probability, and a tabular breakdown of the six facial sub-feature activation scores (periocular, nasolabial, hairline, forehead, chin/jaw, background). The heatmap image is received as a base64-encoded PNG string in the JSON response and decoded client-side for display.
4.1.2 Threshold Slider Module
The Threshold Slider Module provides interactive classification threshold control. A Streamlit slider widget allows users to adjust the decision boundary between 0.0 and 1.0 (default 0.5). When the threshold is modified, the frontend re-evaluates the prediction label for the current cached result without issuing a new API call. A confusion matrix visualization is updated in real time to show how the threshold change affects classification outcomes across the pre-computed benchmark test set. This module is particularly valuable for educational use, enabling users to understand the precision-recall tradeoff in binary classification.
4.1.3 Cross-Dataset Metrics Module
This module retrieves and displays the pre-computed cross-dataset benchmark results from the /metrics endpoint. It renders an interactive table showing the model's performance across all four evaluation protocols (ID, CD-A, CD-B, CD-C, and CD-C+Aug), with metrics including accuracy, ROC-AUC, F1-score, precision, recall, equal error rate, and average precision. The table is colour-coded by performance level. A supporting text panel explains each protocol in plain language, helping non-technical users interpret the generalization gap between in-domain and cross-dataset results.
4.1.4 Artifact Glossary Module
The Artifact Glossary provides an educational reference linking common deepfake visual artifacts to their corresponding facial anatomical regions and detection signatures. Each entry includes: the artifact name (e.g., blending boundary, GAN spectral artifacts, compression blocking), a plain-language description, the facial region where it typically manifests, and a reference to the Grad-CAM activation region that the model associates with detecting it. This module contextualizes the Grad-CAM heatmaps for non-expert users.
4.1.5 Error Gallery Module
The Error Gallery presents a curated collection of false positive and false negative prediction examples drawn from the test set. Each gallery entry shows the original image, the Grad-CAM heatmap, the predicted confidence score, the ground truth label, and a qualitative explanation of why the model was incorrect. The gallery is organized by error type: StyleGAN3 failures (high-quality synthesis that evades detection), beauty-filter false positives (real images misclassified due to skin smoothing), and heavy-compression false negatives (deepfakes where compression destroys artifact patterns). This module is intended to build user calibration — understanding the system's failure modes before relying on its predictions.
4.1.6 Feedback and Audit Report Modules
The Feedback Module allows users to submit per-prediction assessments, indicating whether the prediction aligns with their own judgment. Feedback is logged to a local JSON file for offline analysis. The Audit Report Export Module generates a structured PDF document per prediction session. The report is assembled from: the input image thumbnail, its SHA-256 hash, the UTC prediction timestamp, the prediction label and confidence, the decision threshold applied, the Grad-CAM heatmap image, the sub-feature activation scores, and model provenance metadata. The report uses the ReportLab Python library for PDF generation and is downloadable directly from the Streamlit interface.

4.2 Backend Layer – FastAPI Application
The backend layer is implemented as a FastAPI application that exposes the system's inference capabilities as a documented REST API. FastAPI is instantiated as a single ASGI application served by Uvicorn. The application registers three primary routes and applies startup event handlers for model initialization. All request bodies are validated using Pydantic models, and all responses are structured JSON objects with well-defined schemas.
4.2.1 Startup and Model Loading
On application startup, FastAPI executes an @app.on_event('startup') handler that: determines the available compute device (CUDA GPU if available, else CPU), loads the pre-trained EfficientNet-B0 weights from the serialized .pt checkpoint file, instantiates the classification head, moves all parameters to the selected device, sets the model to evaluation mode (model.eval()), and disables gradient computation for inference (torch.no_grad() context). The model is stored as an application-level state variable, ensuring it is loaded exactly once and reused across all subsequent inference requests without reloading from disk. Model loading typically completes within 2-4 seconds on first startup. MTCNN is also instantiated at startup with device-aware configuration.
4.2.2 POST /predict/image Endpoint
The /predict/image endpoint accepts a multipart/form-data POST request containing a single image file. The endpoint handler: (1) reads the uploaded file bytes and decodes to a PIL Image object, (2) passes the image through the MTCNN face detection pipeline to obtain the cropped face region, (3) applies the standard preprocessing transforms (resize to 224x224, normalize with ImageNet statistics), (4) runs forward inference through EfficientNet-B0 and sigmoid activation to obtain a confidence score, (5) runs the Grad-CAM pipeline to generate the attention heatmap, (6) computes per-region activation scores from the heatmap, (7) encodes the heatmap overlay as a base64 PNG string, and (8) serializes and returns a JSON response object containing all results.
The JSON response schema for /predict/image contains: label (string: 'REAL' or 'FAKE'), confidence (float: 0.0-1.0), heatmap_b64 (string: base64-encoded PNG), region_scores (object: dict of six float values for anatomical regions), inference_time_ms (float), face_detected (boolean), face_confidence (float: MTCNN score).

4.2.3 POST /predict/video Endpoint
The /predict/video endpoint accepts a multipart/form-data POST request containing a video file (MP4, AVI, MOV). The handler: (1) saves the file to a temporary path, (2) opens the video with OpenCV VideoCapture, (3) extracts frames at the configured sampling rate (default 1fps, configurable via query parameter), (4) applies the preprocessing pipeline to each frame independently, (5) batches frames into groups of 8 for GPU efficiency, (6) runs batch inference, (7) aggregates results. The response contains: per_frame_labels (list), per_frame_confidence (list), mean_confidence (float), fraction_fake (float), timeline (list of floats for visualization), total_frames_sampled (int).
4.2.4 GET /metrics Endpoint
The /metrics endpoint returns a pre-computed JSON object containing the cross-dataset benchmark results across all evaluation protocols. The data is loaded from a static metrics.json fixture file at startup and returned without any computation at request time. This ensures that the metrics endpoint remains available even when GPU resources are under load from concurrent inference requests. The response is cached with an ETag header to avoid redundant data transfer.
4.3 ML Inference Layer – EfficientNet-B0
The ML Inference Layer is the computational core of the system. It encapsulates the EfficientNet-B0 backbone, the classification head, and the forward inference logic. This layer is instantiated once at startup and operates exclusively in evaluation mode to prevent gradient accumulation and batch normalization from affecting inference consistency.
4.3.1 EfficientNet-B0 Backbone Architecture
EfficientNet-B0 implements the compound scaling methodology, uniformly scaling network depth, width, and resolution using a fixed set of scaling coefficients (depth=1.0, width=1.0, resolution=224). The backbone consists of seven Mobile Inverted Bottleneck Convolution (MBConv) stages with Squeeze-and-Excitation (SE) attention blocks. The final stage produces a 1280-dimensional feature vector via Global Average Pooling (GAP). The backbone contains approximately 4.0M of the system's 5.3M total parameters.
The backbone's Squeeze-and-Excitation blocks are architecturally significant for deepfake detection because they enable the network to selectively re-weight channel feature maps based on global context. This channel attention mechanism allows the network to learn that certain frequency-domain features — corresponding to GAN spectral fingerprints or blending boundary gradients — are more discriminative than texture or color features, improving generalization across different deepfake synthesis techniques.
4.3.2 Classification Head
The classification head appended to the EfficientNet-B0 backbone consists of: a Global Average Pooling layer reducing the final feature map to a 1280-dimensional vector, a Dropout layer with p=0.3 for regularization, a fully connected Dense layer mapping 1280 → 512 dimensions with ReLU activation, a second Dropout layer with p=0.2, and a final Dense layer mapping 512 → 1 with Sigmoid activation producing the probability score P(fake | image). The Sigmoid output is thresholded at 0.5 by default to produce the binary label.
4.3.3 Two-Phase Fine-Tuning Protocol
The model is fine-tuned using a two-phase protocol designed to leverage ImageNet pretrained features while adapting them to the deepfake detection domain. In Phase 1, all backbone layers are frozen and only the classification head is trained for 5 epochs with learning rate 1e-4 and batch size 32. This establishes stable classifier weights before beginning end-to-end tuning. In Phase 2, the top 30 layers of the EfficientNet-B0 backbone are unfrozen and the entire model is trained end-to-end for 25 epochs with a reduced learning rate of 1e-5, AdamW optimizer with weight decay 1e-4, and cosine annealing learning rate schedule.
Phase 2 training uses a composite loss function combining binary cross-entropy with label smoothing (epsilon=0.1) to prevent overconfident predictions on the training set. Mixed precision training (torch.cuda.amp) is applied to reduce VRAM consumption and accelerate training on CUDA GPUs. Training runs are monitored with validation AUC at each epoch, and the best checkpoint (highest validation AUC) is retained for inference deployment.
4.4 Explainability Layer – Grad-CAM Engine
The Grad-CAM Engine is an inference-time component that generates spatial attention maps for every prediction. It is implemented as a Python class that registers forward hooks on the final convolutional block of EfficientNet-B0 to capture intermediate feature activations and backward hooks to capture gradients during a synthetic backward pass triggered after the forward inference.
4.4.1 Grad-CAM Computation Pipeline
The Grad-CAM computation follows the algorithm: (1) the preprocessed face tensor is passed through a forward pass with gradient tracking enabled (torch.enable_grad() within a torch.no_grad() context override); (2) the activation maps A from the final convolutional block are captured via a registered forward hook; (3) the model output score for the target class (fake=1) is backpropagated, and gradients dY/dA are captured via a registered backward hook; (4) the gradients are spatially pooled via Global Average Pooling to obtain importance weights alpha_k for each feature map channel k; (5) a weighted linear combination of the activation maps is computed: L = ReLU(sum_k alpha_k * A_k); (6) the resulting 7x7 heatmap L is bilinear-upsampled to 224x224 resolution matching the input; (7) L is normalized to [0,1] and applied as a Jet colormap overlay on the original face image with alpha=0.5.
4.4.2 Facial Region Score Computation
The heatmap L is partitioned into six anatomical face regions using pre-computed binary mask templates calibrated to the 224x224 normalized face coordinate system. The masks are derived from the 68-point facial landmark model applied to the HELEN face segmentation dataset, covering: periocular region (eyes and immediate surround), nasolabial region (nose, upper lip, and fold), hairline and upper forehead region, mid-forehead region, chin and jaw region, and background (non-face pixels). For each region, a mean activation score is computed from the intersection of the heatmap values and the corresponding binary mask. These six scores provide a quantitative summary of which facial anatomical regions contributed most to the deepfake prediction, enabling forensic attribution of the model's decision.

5. Data Architecture
5.1 Data Flow Overview
The system's data architecture encompasses two distinct data flows: the offline training data pipeline and the online runtime inference data flow. These flows share some preprocessing logic but are architecturally separate, as the training pipeline is executed once offline and its output (the model checkpoint) is consumed by the runtime inference system.
The offline training data flow begins with raw video frames sourced from three benchmark datasets and culminates in a serialized model checkpoint. The runtime inference data flow begins with a user-provided image or video file and culminates in a JSON API response containing the prediction, confidence, and Grad-CAM visualization.
5.2 Multi-Source Dataset Architecture
The training corpus is assembled from three publicly available deepfake benchmark datasets: FaceForensics++ (FF++), Celeb-DF v2, and the Deepfake Detection Challenge (DFDC). These datasets collectively cover a diverse range of deepfake synthesis techniques, source video qualities, and compression levels, providing a representative training distribution for generalized detection.
Frame selection within each dataset follows a uniform random sampling strategy with stratified balancing to ensure equal representation of real and fake frames in the combined corpus. Frames are sampled at scene diversity-aware intervals to minimize temporal redundancy. From FaceForensics++, frames are drawn from all four manipulation categories (DeepFakes, FaceSwap, NeuralTextures, Face2Face) with equal representation to ensure the model is exposed to diverse synthesis artifacts.
5.3 Preprocessing Pipeline Architecture
All frames from all three datasets pass through a unified preprocessing pipeline before training or inference. The pipeline is implemented as a modular Python class with configurable parameters and consistent behavior across training and inference modes. Consistency between training and inference preprocessing is architecturally critical: any discrepancy introduces a domain shift that degrades inference accuracy.
5.3.1 Face Detection Stage
The first stage of the preprocessing pipeline applies MTCNN (Multi-Task Cascaded Convolutional Networks) face detection to each input frame. MTCNN is a three-stage cascaded network (P-Net, R-Net, O-Net) that simultaneously detects face bounding boxes and 68-point facial landmarks. The confidence threshold is set to 0.9 to minimize false detections. Only the highest-confidence detected face is retained from each frame. If MTCNN fails to detect a face above the confidence threshold, RetinaFace is invoked as a fallback detector. Frames for which neither detector finds a qualifying face are discarded from the training corpus.
5.3.2 Cropping and Alignment Stage
The detected face bounding box is expanded by a 20% contextual border margin in each direction to include periocular context and avoid tight cropping that removes blending boundary artifacts. The expanded crop is then geometrically aligned using a similarity transformation derived from the 68 detected facial landmarks, normalizing the face to a canonical frontal orientation. Specifically, the alignment targets a reference configuration derived from the average face geometry in the HELEN dataset, placing the eye centers, nose tip, and mouth corners at consistent positions relative to the 224x224 output frame. This alignment is computed using a least-squares similarity transformation estimated via the Umeyama algorithm.
5.3.3 Resizing and Normalization Stage
The aligned face crop is bicubic-upsampled or downsampled to exactly 224x224 pixels, matching the input resolution expected by the EfficientNet-B0 backbone. The pixel values are normalized using the ImageNet channel statistics: mean=[0.485, 0.456, 0.406] and standard deviation=[0.229, 0.224, 0.225] applied independently to each RGB channel. This normalization is mandatory for transfer learning from ImageNet pretrained weights, as the backbone's initial feature representations are calibrated to this statistical distribution.
5.3.4 Training-Time Augmentation Stage
During training, additional stochastic augmentations are applied to improve regularization and cross-dataset generalization. The augmentation schedule is applied after normalization to avoid disrupting the ImageNet statistics correction.
5.4 Data Storage Design
The system uses a file-system-based storage design with no relational or NoSQL database. This is appropriate for the academic scope and avoids database administration overhead. All persistent data artifacts are organized within a structured directory tree.
Model Checkpoint: models/efficientnet_b0_deepfake_v1.pt — PyTorch serialized state dict containing all trainable parameters (~21MB). Loaded once at API startup.
Benchmark Metrics Fixture: data/metrics.json — pre-computed evaluation results for all four protocols, served by the /metrics endpoint without runtime recomputation.
Face Region Masks: data/face_masks/*.npy — NumPy binary mask arrays for each of the six anatomical face regions, used by the Grad-CAM region scoring module.
Feedback Log: logs/feedback.json — append-only JSON log of user feedback submissions from the Streamlit interface. Rotated daily.
Training Data Cache: data/frames/{dataset}/{split}/ — preprocessed and aligned face frames stored as PNG files organized by dataset and train/val/test split. Used only during offline training.
Audit Reports: reports/{timestamp}_report.pdf — generated audit report PDFs stored in a timestamped reports directory, retained for the session duration.


5.5 Data Exchange Contracts
5.5.1 POST /predict/image Request Contract
Request content type: multipart/form-data. Required field: file (binary image data, MIME type image/jpeg, image/png, or image/webp). Maximum file size: 10MB. The image must contain at least one detectable human face. Optional query parameters: threshold (float, 0.0-1.0, default 0.5) — the classification decision threshold; return_heatmap (boolean, default true) — whether to include base64 heatmap in response.
5.5.2 POST /predict/image Response Contract
Response content type: application/json. Response schema: { label: string ('REAL'|'FAKE'), confidence: float [0.0,1.0], heatmap_b64: string|null (base64 PNG), region_scores: { periocular: float, nasolabial: float, hairline: float, forehead: float, chin_jaw: float, background: float }, inference_time_ms: float, face_detected: boolean, face_confidence: float, model_version: string, threshold_applied: float }. HTTP status 200 on success, 422 if face detection fails, 400 if file is invalid.
5.5.3 POST /predict/video Response Contract
Response content type: application/json. Response schema: { per_frame_labels: [string], per_frame_confidence: [float], mean_confidence: float, fraction_fake: float, timeline: [float], total_frames_sampled: integer, video_duration_seconds: float, fps_processed: float, inference_time_ms: float }. The timeline array contains one confidence value per sampled frame in temporal order, enabling visualization of manipulation onset and offset within the video.
5.5.4 GET /metrics Response Contract
Response content type: application/json. Response schema: { protocols: [ { name: string, description: string, train_datasets: [string], test_dataset: string, accuracy: float, roc_auc: float, f1_score: float, precision: float, recall: float, eer: float, average_precision: float } ] }. The ETag header is set based on the metrics fixture file hash; clients should implement conditional GET caching.
Frequency of data exchanges: the /predict/image endpoint is called once per user image upload; the /predict/video endpoint is called once per video upload and may take 10-60 seconds for longer videos; the /metrics endpoint is called once on frontend page load and subsequently served from browser cache. All API endpoints are stateless — no session state is maintained between requests.

6. Component Architecture
6.1 Component Breakdown
The system is decomposed into twelve principal software components organized across the five architectural layers. Each component has a single, well-defined responsibility, a defined interface through which it communicates with adjacent components, and independently testable internal logic.
6.2 Component Interfaces and APIs
6.2.1 FacePreprocessor Interface
The FacePreprocessor exposes a single primary method: preprocess(image: PIL.Image, augment: bool = False) -> tuple[torch.Tensor, dict]. The method returns a normalized 224x224 tensor ready for model inference and a metadata dictionary containing the detected bounding box, MTCNN confidence score, alignment transform parameters, and a face_detected boolean flag. When augment=True, the training augmentation schedule is applied. All internal face detection, alignment, and normalization logic is encapsulated within this interface, making the preprocessing stage independently testable and substitutable.
6.2.2 InferenceEngine Interface
The InferenceEngine exposes: predict(tensor: torch.Tensor) -> tuple[float, str] returning (confidence, label), and predict_batch(tensors: list[torch.Tensor]) -> list[tuple[float, str]] for batch inference. The engine maintains the model in GPU memory and applies automatic mixed precision (AMP) during inference. The interface is stateless from the caller's perspective — the same engine instance can service concurrent requests safely because inference runs within torch.no_grad() with no shared mutable state beyond the model parameters.
6.2.3 GradCAMEngine Interface
The GradCAMEngine exposes: compute(tensor: torch.Tensor, label: str) -> GradCAMResult. The GradCAMResult dataclass contains: heatmap (numpy.ndarray 224x224), overlay_image (PIL.Image with heatmap blended), heatmap_b64 (base64 string), region_scores (dict[str, float] with six anatomical region scores). The engine registers and deregisters forward/backward hooks per invocation to avoid hook accumulation across multiple calls.
6.3 Component Dependency Map
The dependency relationships between components follow a strict layered topology with no circular dependencies. The Presentation Layer depends exclusively on the API Gateway Layer via HTTP; it has no direct dependency on the Inference or Data Processing layers. The API Gateway Layer depends on the Inference and Data Processing layers via in-process Python function calls. The Inference Layer depends on the Explainability Layer for post-prediction Grad-CAM computation. The Data Processing Layer has no upward dependencies, serving as the lowest-level foundational component.
External library dependencies are contained within specific components to minimize coupling: PyTorch and timm are exclusively imported within InferenceEngine; MTCNN and RetinaFace are exclusively within FacePreprocessor; OpenCV is used in FacePreprocessor (for alignment transforms) and VideoFrameExtractor (for video I/O) and GradCAMEngine (for image processing); ReportLab is exclusively within AuditReporter. This containment strategy ensures that substituting any external library requires changes to only one component.

8. Class Architecture
8.1 Core Classes and Responsibilities
8.1.1 DeepfakeDetector (Core Model Class)
The DeepfakeDetector class encapsulates the complete model architecture — the EfficientNet-B0 backbone and the classification head — as a single nn.Module subclass. This class is instantiated once at API startup and serialized to disk after training as a PyTorch state dictionary.
Attributes: backbone (nn.Module): EfficientNet-B0 from timm with pretrained ImageNet weights; head (nn.Sequential): classification head (GAP → Dropout(0.3) → Linear(1280,512) → ReLU → Dropout(0.2) → Linear(512,1) → Sigmoid); device (torch.device): CUDA or CPU.
Methods: forward(x: Tensor) -> Tensor: standard PyTorch forward pass returning sigmoid output; predict(x: Tensor) -> tuple[float, str]: single-sample inference with label threshold application; predict_batch(xs: Tensor) -> list[tuple]: batch inference with AMP.
Design Notes: Inherits from nn.Module to integrate with PyTorch's parameter management, device movement (to(device)), and gradient computation framework. The backbone and head are stored as named child modules to enable layer-selective unfreezing during Phase 2 fine-tuning.
8.1.2 GradCAMEngine
The GradCAMEngine class implements the Gradient-weighted Class Activation Mapping algorithm. It maintains references to the target convolutional layer and registers PyTorch hooks to intercept activations and gradients.
Attributes: model (DeepfakeDetector): reference to the inference model; target_layer (nn.Module): the final MBConv block of EfficientNet-B0; activations (Tensor): captured forward activations; gradients (Tensor): captured backward gradients; masks (dict[str, ndarray]): six pre-computed anatomical face region binary masks.
Methods: register_hooks(): installs forward and backward hooks on target_layer; remove_hooks(): deregisters hooks after computation; compute(tensor, label) -> GradCAMResult: executes full Grad-CAM pipeline and returns result dataclass; _compute_region_scores(heatmap) -> dict: computes mean activation per anatomical region.
Design Pattern: Uses the Observer pattern via PyTorch hooks — the engine observes intermediate computations of the DeepfakeDetector without modifying its forward pass logic. Hooks are registered and removed per inference call to prevent accumulation.
8.1.3 FacePreprocessor
The FacePreprocessor class encapsulates all face detection, alignment, and normalization logic. It maintains MTCNN and RetinaFace detector instances as attributes and applies the Umeyama alignment transform for geometric normalization.
Attributes: mtcnn (MTCNN): primary face detector; retina_face (RetinaFace): fallback detector; transform (Compose): torchvision transform chain (Resize, ToTensor, Normalize); augment_transform (Compose): training augmentation pipeline; margin_ratio (float): 0.20 default crop margin.
Methods: detect_face(image) -> tuple[ndarray|None, float]: returns cropped face array and detection confidence; align_face(face, landmarks) -> ndarray: applies Umeyama similarity transform; preprocess(image, augment=False) -> tuple[Tensor, dict]: full preprocessing pipeline entry point; _expand_bbox(bbox, margin) -> tuple: expands bounding box by margin_ratio.
8.1.4 VideoFrameExtractor
The VideoFrameExtractor class handles video file I/O and frame-level inference orchestration. It coordinates FacePreprocessor and InferenceEngine over a sequence of video frames.
Attributes: fps_target (float): target sampling rate (default 1.0fps); batch_size (int): inference batch size (default 8); preprocessor (FacePreprocessor); engine (InferenceEngine).
Methods: extract_frames(video_path: str) -> list[PIL.Image]: samples frames at fps_target; process_video(video_path: str) -> VideoResult: orchestrates frame extraction, preprocessing, batched inference, and result aggregation; _aggregate_results(frame_results) -> dict: computes mean_confidence, fraction_fake, timeline.
8.1.5 AuditReporter
The AuditReporter class assembles forensic audit report PDFs from prediction metadata using the ReportLab library.
Attributes: page_size (tuple): PDF page dimensions; styles (StyleSheet1): ReportLab paragraph styles; output_dir (Path): reports output directory.
Methods: generate_report(prediction_result: PredictionResult, image: PIL.Image) -> Path: main entry point returning path to generated PDF; _build_cover_section(doc, result): adds header, image, hash, timestamp; _build_results_section(doc, result): adds prediction label, confidence, threshold; _build_heatmap_section(doc, result): embeds heatmap PNG and region score table; _build_provenance_section(doc): adds model metadata.
8.1.6 FastAPI Route Handlers
Route handler functions are not classes but are implemented as async Python functions decorated with @app.post and @app.get. They hold no state and depend on module-level singleton instances of FacePreprocessor, InferenceEngine, and GradCAMEngine initialized at startup. Handler functions: predict_image(file: UploadFile, threshold: float = 0.5) -> PredictionResponse; predict_video(file: UploadFile, fps: float = 1.0) -> VideoResponse; get_metrics() -> MetricsResponse.
8.2 Class Relationships and Inheritance
The class hierarchy reflects a composition-over-inheritance design philosophy. DeepfakeDetector inherits from torch.nn.Module (PyTorch requirement for parameter management). All other classes are plain Python classes (no inheritance hierarchy) composed via dependency injection.
Composition: FastAPI route handlers hold references to FacePreprocessor, InferenceEngine, and GradCAMEngine. GradCAMEngine holds a reference to DeepfakeDetector (not a subclass). VideoFrameExtractor holds references to FacePreprocessor and InferenceEngine.
Data Transfer Objects: PredictionResult, VideoResult, GradCAMResult, and MetricsResponse are Python dataclasses used to pass structured data between components without coupling to JSON serialization concerns. Pydantic models at the API layer convert these dataclasses to JSON response objects.
Singleton Pattern: FacePreprocessor, InferenceEngine, and GradCAMEngine are instantiated as module-level singletons at FastAPI startup. This ensures the GPU model is loaded once and shared across all request handlers, preventing redundant loading.

10. Deployment Architecture
10.1 Infrastructure Overview
The Deepfake Detection System is deployed as a single containerized application on a CUDA-enabled host machine. The deployment topology consists of a single Docker container encapsulating both the FastAPI backend (served by Uvicorn ASGI server) and the Streamlit frontend (served by Streamlit's built-in Tornado server). Both services share the same container filesystem, model checkpoint file, and GPU device.
The host machine for production inference is an NVIDIA RTX 3060 equipped workstation running Ubuntu 22.04 LTS with CUDA 11.8 and cuDNN 8.6. Development and local inference is supported on Apple Silicon M2 (MacBook Pro) using PyTorch's MPS (Metal Performance Shaders) backend, which achieves 312ms per-image latency. CPU-only inference is supported on any x86-64 Linux host but latency exceeds 1000ms per image.
10.2 Environment Configuration
Environment-specific configuration is managed through a .env file loaded at application startup using python-dotenv. The following environment variables are configurable: MODEL_PATH (path to .pt checkpoint), DEVICE (cuda|mps|cpu, auto-detected if not set), DEFAULT_THRESHOLD (float, default 0.5), MAX_IMAGE_SIZE_MB (int, default 10), VIDEO_SAMPLE_FPS (float, default 1.0), BATCH_SIZE (int, default 8), REPORTS_DIR (path, default ./reports).
10.3 Containerization Strategy
The system is containerized using Docker with NVIDIA Container Toolkit for GPU passthrough. A single Dockerfile defines the complete runtime environment, using the nvidia/cuda:11.8.0-cudnn8-runtime-ubuntu22.04 base image.
10.3.1 Docker Image Structure
The Docker image build proceeds through the following layers: (1) Base: nvidia/cuda:11.8.0-cudnn8-runtime-ubuntu22.04 providing CUDA runtime and cuDNN; (2) System packages: Python 3.10, pip, libGL (for OpenCV), libglib2.0 (for Pillow); (3) Python dependencies: PyTorch 2.0+cu118 (from PyTorch wheel index), timm, fastapi, uvicorn, streamlit, opencv-python-headless, facenet-pytorch (MTCNN), reportlab, python-dotenv, scikit-learn (pinned versions in requirements.txt); (4) Application code: copied to /app; (5) Model weights: copied to /app/models; (6) Data fixtures: copied to /app/data; (7) Entry point: startup.sh launching Uvicorn on port 8000 and Streamlit on port 8501 simultaneously via process supervision.
10.3.2 Port Mapping and Networking
The container exposes ports 8000 (FastAPI / Uvicorn) and 8501 (Streamlit). On the host machine, both ports are bound to localhost only (127.0.0.1:8000 and 127.0.0.1:8501) to prevent unintentional external exposure. The Streamlit frontend communicates with FastAPI via the container's loopback interface (http://localhost:8000). GPU passthrough is enabled via the --gpus all flag in the docker run command, granting the container access to all NVIDIA GPUs available on the host.
10.3.3 Model Weight Management
The model checkpoint file (efficientnet_b0_deepfake_v1.pt, approximately 21MB) is included in the Docker image at build time. This approach ensures that the image is self-contained and reproducible. An alternative production pattern would mount the checkpoint as a Docker volume to enable model updates without rebuilding the image, which is recommended for future deployment versions. The checkpoint contains only the PyTorch state dictionary (model weights and biases), not the full optimizer state, reducing file size while preserving all information required for inference.

11. Performance and Scalability
11.1 Inference Latency Benchmarks
Inference latency was benchmarked across three hardware configurations using the same preprocessed 224x224 face tensor. Latency is measured as wall-clock time from the start of model.forward() to the availability of the sigmoid output, excluding face detection preprocessing time (typically 15-30ms) and Grad-CAM computation (typically 25-35ms).
End-to-end API response latency (including face detection, preprocessing, inference, Grad-CAM, and JSON serialization) on the RTX 3060 hardware is approximately 190ms for a single image request. This is well within the 500ms latency target set for interactive web application use cases. The major contributors to end-to-end latency are face detection (MTCNN: ~30ms), image decoding and preprocessing (~25ms), model inference (~87ms), and Grad-CAM computation (~35ms), with JSON serialization and HTTP overhead accounting for the remaining ~13ms.


11.2 Memory Utilization
The model checkpoint loaded into GPU memory occupies approximately 21MB of VRAM in FP32 precision and 11MB in FP16. Including activation buffers for batch size 8 inference and Grad-CAM hook tensors, peak VRAM consumption is approximately 380MB for a single inference request. The RTX 3060's 12GB VRAM comfortably accommodates this, leaving ample headroom for larger batch sizes or parallel requests. CPU RAM consumption for the full FastAPI application (model in GPU VRAM, Python interpreter, MTCNN weights, and auxiliary libraries) is approximately 1.8GB.
11.3 Scalability Analysis
In the current monolithic architecture, horizontal scaling (running multiple instances) would require either GPU-capable machines for each instance (expensive) or a load balancer distributing inference requests across instances sharing a common model checkpoint file. Vertical scaling (upgrading to a higher-end GPU such as RTX 4090 or A100) is simpler and would improve throughput proportionally. An A100 80GB GPU would be expected to achieve approximately 12ms per-image inference latency at FP16, enabling batch throughput exceeding 80 images per second.
For future production-scale deployment, the most impactful architectural evolution would be to extract the InferenceEngine into a separate model serving service using NVIDIA Triton Inference Server or TorchServe. These frameworks provide dynamic batching (aggregating concurrent single-image requests into GPU-efficient batches), model versioning, health monitoring, and automatic horizontal scaling based on inference queue depth. However, this evolution would require refactoring the monolithic architecture into a microservices pattern, which is deferred to a future project phase.
11.4 Caching Strategy
The system implements a minimal caching strategy appropriate for its interactive demonstration use case. The /metrics endpoint response is cached indefinitely with an ETag header because benchmark metrics are static between deployments. The Streamlit frontend caches the prediction result in session state to enable threshold adjustment and report export without re-invoking the API. MTCNN model weights are cached to disk by the facenet-pytorch library after first download to avoid repeated network requests. No inference result caching is implemented at the API layer, as inputs are user-provided images with no predictable repetition pattern.

13. Risks, Constraints and Future Roadmap
13.1 Architectural Risks
13.2 Known Architectural Constraints
The following constraints are accepted limitations of the current architectural design, each of which is documented to support informed interpretation of the system's capabilities and boundaries.
No Temporal Modelling: Frames in video analysis are classified independently. GAN artifacts that only manifest across temporal sequences (e.g., temporal flickering, identity drift) are not captured by the current per-frame approach. A future LSTM or transformer-based temporal fusion module would address this.
Single-Face Input Constraint: Only one face per image/frame is processed. Multi-person scenes are handled by selecting the highest-confidence detection, which may not always be the manipulated subject in a composite fake.
No Adversarial Robustness: The model has not been trained with adversarial examples. A determined adversary aware of the model architecture could potentially craft input perturbations that cause misclassification with high confidence.
Monolithic Vertical Scaling Ceiling: Inference throughput is limited by the capacity of a single GPU. Surpassing ~25 images/second would require either a higher-end GPU or architectural evolution to distributed inference.
Streamlit Session State Volatility: Streamlit session state is in-memory and lost on browser refresh. The cached prediction result (used for threshold adjustment and report export) requires re-upload after a session reset.
13.3 Future Architectural Roadmap
13.3.1 Phase 2: Temporal Modelling Extension
The planned Phase 2 architectural extension introduces a BiLSTM temporal fusion module that processes sequences of per-frame feature vectors (extracted from the EfficientNet-B0 penultimate layer) to model temporal consistency across video frames. This would replace the statistical aggregation currently used in the VideoFrameExtractor with a sequence-aware prediction that captures temporal artifacts. The BiLSTM module would be trained on the existing corpus with temporal sequence labels and deployed as an additional component in the Inference Layer, requiring no changes to the API contract.

13.3.2 Phase 3: Adversarial Training
Phase 3 introduces adversarial training using FGSM (Fast Gradient Sign Method) and PGD (Projected Gradient Descent) attacks during fine-tuning Phase 2. The training pipeline would be augmented with an adversarial example generator that creates perturbed versions of training images at epsilon=8/255 (L-infinity norm), which are mixed into the training batch at a 30% ratio. This significantly improves robustness against adversarially optimized deepfake content without major changes to the inference architecture.
13.3.3 Phase 4: Multi-Modal Audio-Visual Detection
Phase 4 introduces a multi-modal detection architecture that jointly processes visual facial features and audio speech features. Deepfake videos frequently exhibit audio-visual synchronization artifacts — subtle mismatches between lip movements and speech audio — that are invisible from visual features alone. The Phase 4 architecture would add an audio feature extraction branch (using Wav2Vec2 or HuBERT transformer) and a cross-modal attention fusion module that combines visual and audio embeddings before the classification head. This architectural evolution would require the /predict/video endpoint to accept video files with audio streams and the response to include audio-visual synchronization scores.
13.3.4 Phase 5: Distributed Inference Service
Phase 5 transforms the monolithic architecture into a hybrid microservices topology where the InferenceEngine is extracted into an NVIDIA Triton Inference Server instance exposing a gRPC model serving interface. The FastAPI application layer would communicate with Triton via gRPC, enabling dynamic batching, model versioning, A/B testing of model updates, and horizontal scaling of the inference service independently from the API gateway. This evolution would require Kubernetes orchestration, a service mesh (Istio), and a model registry (MLflow or BentoML) for production-grade deployment.
13.4 Compliance and Reproducibility
The system is designed for full experimental reproducibility. All random seeds are fixed (torch.manual_seed(42), numpy.random.seed(42), random.seed(42)) in the training pipeline. Data splits are deterministic, generated from a fixed random seed and stored as CSV manifests. Model checkpoints are versioned with semantic version numbers and SHA-256 hashes in the model registry. The complete training configuration is logged using Python's logging module to a timestamped run directory. A requirements.txt with fully pinned dependency versions and a Dockerfile with a pinned base image ensure that the training environment can be exactly reproduced on any CUDA-capable host.
The project adheres to the research ethics guidelines of SRM Institute of Science and Technology. All training data is sourced from publicly available benchmarks licensed for research use. No personally identifiable information of real individuals is processed or stored beyond what is present in the original benchmark datasets. The system includes clear labelling in the Streamlit interface indicating that it is an experimental research tool and that its predictions should not be relied upon as the sole basis for any consequential decision.
